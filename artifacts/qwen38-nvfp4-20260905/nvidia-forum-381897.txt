 Everyone seems to have settled into two camps with this model: SGLang on two Sparks, or vLLM on one. Nobody had tried the obvious third thing — vLLM across four Sparks at TP4 — so I did. Weight sharding is what buys the room back. The 1M rung: half-conquered, honestly reported The 1M YaRN lane boots and serves : a 4,996k-token KV pool — 4.78x a full 1,048,576-token request — and NIAH-128k passes at every depth. Then the interesting part: the ~3rd request deeper than ~100k tokens wedges a GPU stream and takes the engine with it. I’ve eliminated prefix caching, MTP, CUDA graphs ( --enforce-eager dies identically), allocator settings, page cache, chunk size, and one very educational systemd unit — one variable per boot, on a rebooted fleet each time. The captured py-spy stack and the full isolation matrix are in the repo’s docs/OPEN-PROBLEMS.md ; one suspect remains before this goes upstream as a kernel bug. So: the 262k lane above is the shipped default, the 1M lane is experimental — a config that answers one 1M-deep prompt is not a config that works. What actually happened when I hit “launch” Boot #1 died in seconds. Boot #2 died differently — which on GB10 counts as progress. Three fixes later it serves, and none of them appear in any single- or dual-node recipe (all are launcher defaults in the repo now): Plain TP4 cannot load this checkpoint. At all. TP sharding slices the MoE intermediate 640 → 160 per rank, and the NVFP4 FLASHINFER_CUTLASS backend answers with NotImplementedError: Intermediate size padding for w1 and w3 . The cure is --enable-expert-parallel : don’t slice the experts, deal them out whole — 512/4 = 128 per rank. Your fd limit is about to overflow and you don’t know it yet. The PLE n-gram table is 128 memmapped safetensors shards . Add the socket storm of 4-node NCCL + EP on top and Docker’s default nofile folds — OSError: [Errno 24] Too many open files , ten minutes into the boot, deep inside PLE setup. --ulimit nofile=1048576 and it never bothers you again. Do not hardcode NCCL_IB_GID_INDEX . After a link bounce, the RoCE v2 GID can land on a different index on one node (I caught index 4 vs 3 fleet-wide). A pinned index then reads a zero GID and NCCL greets you with unhandled system error at init. With NCCL_IB_ROCE_VERSION_NUM=2 and NCCL_IB_ADDR_RANGE set, NCCL picks the right GID per device by itself. Free ops lesson, learned the slow way Do not move a 122 GiB checkpoint between Sparks over ssh. One AES stream pins a GB10 ARM core at ~1 Gbps and your afternoon is gone. A read-only rsync daemon on the compute rails does it at ~16 Gbps — ~2 minutes per node . Script’s in the repo, along with the image fan-out that verifies the docker image ID (not the tag) on every node before any launch. What’s in the repo A Dockerfile over the official day-0 vLLM image with the known GB10 patch stack vendored in, a 4-node worker-first launcher with the full NCCL env, fleet scripts (weight/image fan-out, preflight, teardown, self-healing watchdog), the gate suite, and the bench harness that produced every number above.
